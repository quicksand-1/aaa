# X 系列 AI 组件汇报稿

## 1. 汇报主题

本次汇报的对象，是近期在前端侧建设的一批 `src/X*` 组件。  
它们不是几个彼此独立的小控件，而是一套面向 AI 场景的前端基础能力，覆盖了输入、展示、模型配置和 Agent 编排四个层面。

这次汇报主要回答 4 个问题：

- 我们最近具体做了什么
- 这批组件解决了什么问题
- 当前能力已经走到什么阶段
- 后续应该沿什么方向继续演进

---

## 2. 为什么要做这套组件

在 AI 场景里，前端如果只把模型调用看成一次普通接口请求，通常会遇到几个问题：

- 业务每接一个场景，都要重新做输入框、消息区、历史记录、草稿缓存
- 模型配置分散在代码和页面里，切换、测试、排查都不方便
- 多轮对话、补充参数、确认执行这类流程，容易直接写成页面分支逻辑，后续越来越难维护
- 不同业务都在做“类似但不完全一样”的 AI 页面，重复开发成本高

所以这批 `X*` 组件的目标，不是做一个聊天页面，而是沉淀一套可复用的 AI 前端底座。

它要解决的核心问题是：

- 把重复建设收敛成公共能力
- 把 AI 交互从页面实现提升到组件和运行机制层面
- 为后续更多业务接入提供统一标准

---

## 3. 当前组件全景

目前这套能力可以分成 4 层。

### 3.1 输入层

代表组件：`Xsender`

职责：

- 统一用户输入行为
- 提供建议词触发能力
- 管理历史记录和草稿缓存
- 屏蔽键盘交互细节
- 对外暴露最小但够用的输入控制 API

这意味着业务侧不需要再重复处理：

- 上下键翻历史
- 草稿自动恢复
- Enter / Shift + Enter 的提交行为
- 快捷模板插入

### 3.2 展示层

代表组件：`Xmessages`、`Xmarkdown`

职责：

- 统一消息列表渲染
- 按角色控制左右布局、头像、状态
- 处理空态、加载态和“加载更多”
- 提供 Markdown / Latex 的默认渲染能力

这层解决的是“消息怎么展示”而不是“数据从哪来”，因此可复用性比较高。

### 3.3 配置层

代表组件：`Xllm`

职责：

- 管理 LLM 配置
- 支持新增、编辑、复制、删除
- 支持启用和停用
- 支持连接测试

它把原来容易散落在环境变量、页面配置和调试代码里的模型参数，收口成统一入口。

### 3.4 编排层

代表组件：`Xagent`

职责：

- 管理 capability 路由
- 驱动 function-calling 流程
- 维护 sessionState
- 处理缺参澄清
- 持续累计简化后的对话记忆

这一层说明项目已经不只是“前端调一下模型接口”，而是在前端侧形成了可持续扩展的 Agent 运行框架。

## 4. 已完成的核心能力

### 4.1 输入能力已经形成完整闭环

`Xsender` 当前不是一个简单输入框，而是一个带运行规则的输入内核。

已经具备的能力包括：

- 建议词触发与插入
- 历史记录浏览
- 草稿自动缓存与恢复
- 提交前拦截
- 对外 actionRef 控制
- 与存储层解耦的 provider 设计

这意味着业务如果要接一个新的 AI 场景，输入区的大部分通用问题已经被公共层吃掉了。

### 4.2 消息展示能力已经标准化

`Xmessages` 当前已经定义了比较清晰的消息结构：

- `role`
- `content`
- `status`
- `placement`
- `avatar`
- `extraInfo`
- `bubbleProps`

同时配合 `Xmarkdown`，文本消息默认就支持 Markdown 和 Latex。  
这对 AI 输出场景非常重要，因为模型结果天然更接近富文本，而不是纯字符串。

### 4.3 模型配置从“写死”变成“可管理”

`Xllm` 已经把模型配置抽成一套前端侧可管理能力：

- 可以在界面上维护多套配置
- 可以切换当前生效配置
- 可以在保存前后做连接测试
- 当前默认适配 Responses 风格接口

这一步的价值不只是方便调试，更关键的是把“调用哪个模型、走哪个网关、参数是否正确”从业务页面里剥离出来。

### 4.4 Agent 运行链路已经成立

`Xagent` 目前最有价值的不是“能回答问题”，而是它已经具备一套比较清晰的运行机制：

- 根据问题在多个 capability 中做路由
- 给当前 capability 组装 system prompt 和 user prompt
- 发起 function-calling 调用
- 执行 tool
- 在参数不足时进入 clarify
- 在成功、澄清、失败后都回写 sessionState

这说明当前系统已经从单轮问答，进入到“多轮可恢复执行”的阶段。

### 4.5 已经明确下一步不是“继续聊天”，而是“结构化交互”

除了当前已经落地的文本澄清链路，`Xagent` 的后续建设方向也已经比较明确。  
在 [document/Xagent/README.md](/Users/chenlong/Desktop/dev/fintech/document/Xagent/README.md) 中，已经提出了 `surfaces` 设计，用来承接 `clarify` 之后的结构化交互。

这个方向的核心不是再做一个新组件，而是把现有的：

- `clarify`
- `pendingClarify`
- `sessionState`
- `Xmessages`
- `FormSchema`

串成一条完整的“中断 - 展示 - 提交 - 恢复执行”链路。

第一阶段只聚焦两类 surface：

- `form`：用于补齐缺失参数
- `confirm`：用于执行前确认

这说明 `Xagent` 的演进方向已经从“能否继续对话”，进入到“能否稳定完成结构化业务交互”的阶段。

### 4.6 `form + confirm` 的协议实现路线将对齐 A2UI

这里的“对齐 A2UI”，不是指前端直接接收模型生成的任意 UI 代码，而是参考 Google `A2UI` 的核心思想，用声明式协议来描述 UI，再由前端用受控组件去渲染。

截至目前公开资料，A2UI 有两个时间点值得关注：

- 2025-12-15，Google 对外公布 A2UI，定位为 `Agent-to-User Interface`
- 2026-04-17，Google 公布 `A2UI v0.9`，开始强调 React renderer、Agent SDK、streaming 和 client-defined functions

这说明 A2UI 的方向已经比较清晰：  
**agent 负责描述“要展示什么交互”，客户端负责决定“用什么可信组件来渲染”。**

对我们来说，这个思路非常适合 `Xagent Surfaces`。

原因在于：

- 我们已经有 `clarify` 和 `pendingClarify`
- 我们已经有 `Xmessages` 作为消息容器
- 我们已经有 `FormSchema` 作为表单能力
- 我们要解决的问题，本质上就是“agent 如何安全地驱动 UI 收集输入”

也就是说，`form + confirm` 不应该被实现成一组写死的页面分支，而应该被实现成一套可声明、可校验、可恢复的 UI 协议。

### 4.7 我们的 `surfaces` 和 A2UI 的关系

两者的关系，不是替代关系，而更像是“当前项目内的收敛实现”和“更通用的开放协议方向”的关系。

可以这样理解：

| 对比项       | 当前 `Xagent Surfaces`                            | A2UI 思路                                |
| :----------- | :------------------------------------------------ | :--------------------------------------- |
| 目标范围     | 先解决 clarify 阶段的结构化交互                   | 让 agent 更广泛地驱动 UI                 |
| 第一阶段能力 | `form`、`confirm`                                 | 通用声明式 UI                            |
| 运行方式     | `clarify -> surface -> clarifyResponse -> resume` | agent 返回 UI 描述，客户端渲染并处理交互 |
| 安全边界     | 前端只渲染受控 surface 类型                       | 客户端持有受信组件目录，不执行任意代码   |
| 当前策略     | 做 A2UI 风格的收敛子集                            | 更通用、更开放的 generative UI 协议      |

所以更准确的表述应该是：

- 我们不会一开始就做完整通用版 A2UI
- 我们会先在 `clarify` 场景中落一个 A2UI 风格的协议子集
- 第一阶段只开放 `form` 和 `confirm`
- 前端仍然严格使用自己的组件目录和校验逻辑

这样做的好处是：

- 可以先解决当前最真实的问题
- 协议方向与外部先进实践一致
- 后续如果要扩展成更多 surface 类型，迁移成本更低

## 5. 这套设计带来的实际价值

### 5.1 对业务接入的价值

后续业务接入新 AI 场景时，可以直接复用：

- 输入框交互
- 消息渲染
- LLM 配置管理
- Agent 基础运行机制

业务层主要关注自己的 capability、tool 和业务数据，不需要重复铺底层设施。

### 5.2 对研发协作的价值

这批组件把很多原来“只能靠口头约定”的能力，收敛成了稳定接口：

- 输入组件和存储 provider 的边界
- 消息结构和渲染协议
- 模型配置结构
- capability / slot / tool / clarify / sessionState 的概念边界

接口一旦稳定，前后端协作和多人并行开发的成本都会下降。

### 5.3 对后续平台化的价值

如果未来 AI 场景继续扩张，这套设计天然适合向平台化演进。

原因在于：

- 组件层已经不是一次性页面代码
- 运行时状态已经有统一模型
- capability 已经开始具备注册和复用的可能
- 前端侧已经形成了一个可扩展的 AI interaction layer

换句话说，现在做的不是一个页面，而是一块基础设施。

### 5.4 对齐 A2UI 的额外价值

如果 `form + confirm` 直接按 A2UI 风格的声明式协议来做，会额外带来几层收益：

- UI 不再是 runtime 写死的页面逻辑，而是协议驱动
- 组件的控制权仍在前端，安全边界更清楚
- 后续可以逐步增加更多 surface，而不用推翻当前实现
- 更容易把当前项目内协议抽成未来的公共标准

这类价值短期可能不如“页面能跑”显眼，但长期会直接决定这套能力能不能继续扩张。

## 6. 当前阶段判断

如果用一句话判断当前进度，可以表述为：

**基础底座已经成型，但离平台化和规模化复用还有一段距离。**

更具体一点，可以拆成 3 个结论。

### 6.1 已经过了原型阶段

因为当前不是只有 UI，也不是只有一个 demo 接口，而是已经形成了：

- 组件分层
- 状态模型
- 可插拔存储
- function-calling 主链路
- clarify 与会话记忆机制

这些都说明系统已经进入工程化建设阶段。

### 6.2 还没有完全进入标准产品阶段

虽然主链路已经具备，但要支撑更多业务稳定复用，还需要补足：

- 文档
- 示例
- 调试手段
- 观测能力
- 更明确的能力注册规范
- 结构化交互协议

### 6.3 当前最重要的不是继续堆功能

当前更重要的是把现有抽象做稳，避免每有一个新场景，就在公共层硬塞一组定制逻辑。  
也就是说，下一步的重点应该是“收敛和标准化”，而不是“快速继续加按钮”。

## 7. 当前存在的不足与风险

### 7.1 `Xllm` 的协议适配还偏单一

目前整体更偏向 Responses 风格接口，这对于当前阶段足够，但如果后续要适配多家模型网关，协议抽象还需要往前再走一步。

### 7.2 `Xsender` 的缓存粒度仍偏全局

当前历史和草稿 provider 更接近全局输入缓存。  
如果后续进入多会话、多业务入口并存的场景，可能需要增加会话级或用户级隔离能力。

### 7.3 `Xmessages` 还可以增强流式体验

目前消息渲染结构已经比较清晰，但在流式输出、增量渲染、局部刷新提示等方面还有提升空间。

### 7.4 `Xagent` 缺少更强的可观测性

当前虽然有 step 和 sessionState，但对调试者来说，还缺少一层更直接的可视化能力，例如：

- 本轮命中了哪个 capability
- 每一步调用了哪个 tool
- 为什么触发 clarify
- sessionState 是怎么变化的

如果后续要让更多同学接入，这部分会越来越重要。

### 7.5 当前澄清能力仍以文本为主

虽然现在已经有 `clarify` 能力，但它本质上还是“让用户再说一句话”。  
这对简单问题足够，但对以下场景并不稳定：

- 一次补多个字段
- 必须输入结构化参数
- 需要显式二次确认的副作用操作

这也是为什么后续需要引入 `surfaces`。  
如果没有这层协议，`Xagent` 很容易停留在“能聊天，但不好真正落业务动作”的阶段。

### 7.6 如果不尽早协议化，后续 UI 会再次碎片化

如果 `form + confirm` 不按协议做，而是每个业务场景单独写页面逻辑，短期虽然快，但很容易重新回到老问题：

- 每个场景都有自己的补参弹窗
- 每个页面都有自己的确认卡片
- 恢复执行逻辑分散在业务代码里
- `clarify` 和 UI 状态难以统一追踪

所以这一步不是“是否需要更优雅”的问题，而是“是否要继续守住底座抽象”的问题。

## 8. 后续发展路线

建议按 4 个阶段推进。

### 8.1 第一阶段：补齐接入资料

重点：

- 为 `Xsender`、`Xmessages`、`Xllm`、`Xagent` 补完整文档
- 提供标准示例
- 明确 capability 和 tool 的接入方式

目标：

- 降低其他业务同学的理解和使用门槛

### 8.2 第二阶段：增强运行时能力

重点：

- 支持流式输出
- 增强消息状态反馈
- 完善会话级缓存和隔离
- 增强异常恢复和重试机制
- 让 `clarify` 支持结构化恢复输入

目标：

- 让这套底座更适合真实业务长期运行

### 8.3 第三阶段：推进标准化

重点：

- 落地 `Xagent Surfaces`
- 支持 `form + confirm` 两类基础交互
- 扩展 `pendingClarify` 和 `sessionState` 结构
- 让 `Xmessages` 支持渲染 `surface` 类型消息
- 复用 `FormSchema` 承接参数补充表单
- 以 A2UI 风格的声明式协议定义 surface
- 统一 capability schema
- 统一 tool 注册约定
- 统一 sessionState 扩展方式
- 增强调试和观测面板

目标：

- 从“可复用组件”向“可复用平台能力”演进

### 8.4 第四阶段：与业务场景双向收敛

重点：

- 结合真实业务场景继续校验抽象是否合理
- 把真正稳定、重复出现的能力沉淀到公共层
- 把过度定制、只服务单一场景的逻辑挡在业务层
- 验证 `surfaceId + surfaceKey + clarifyResponse` 这一套协议是否足够稳定

目标：

- 保持底座稳定，不被单一场景绑架

### 8.5 `Xagent Surfaces` 的单独定位

如果单独看 `Xagent`，后续最关键的一条路线可以单独总结为：

- 当前阶段：已支持文本 clarify
- 下一阶段：升级为结构化 clarify
- 第一批能力：`form` 和 `confirm`
- 设计原则：单轮中断、显式恢复、surface 不直接执行业务、确认后恢复 `pendingAction` 而不是重跑模型

这条路线一旦打通，`Xagent` 的能力边界会明显提升：

- 不只是“模型返回一句追问”
- 而是“前端能稳定收集输入，并把流程续跑下去”

### 8.6 基于 A2UI 思路的建议实现路径

建议把这条路线拆成 6 步，而不是一次做成一个“完全通用 UI 引擎”。

#### 第一步：定义我们自己的 surface envelope

在 `clarify` 结果里保留当前已经设计好的外层结构：

- `type: 'clarify'`
- `answer`
- `sessionState`
- `surface`

其中 `surface` 继续保留：

- `surfaceId`
- `surfaceKey`
- `version`
- `responseType`
- `meta`
- `data`

这一层是我们运行时恢复的锚点，不建议一开始就放弃。

#### 第二步：让 `surface.data` 采用 A2UI 风格的声明式内容

这里的重点不是照搬 Google 全量协议，而是借鉴它的核心约束：

- 数据描述 UI
- 客户端持有组件目录
- 服务端或 runtime 不直接下发可执行代码

对我们第一阶段来说，可以把它收敛成：

- `form surface`：声明字段、标题、默认值、按钮文案
- `confirm surface`：声明摘要、风险级别、确认文案

也就是说，先做一个“面向 clarify 的 A2UI profile”。

#### 第三步：前端维护受控 renderer catalog

前端侧不直接 `eval` 或动态执行任何 UI。  
而是明确维护一套受控映射，例如：

- `surfaceId = form` -> `FormSurfaceRenderer`
- `surfaceId = confirm` -> `ConfirmSurfaceRenderer`

再由渲染器内部去复用现有能力：

- `FormSurfaceRenderer` -> `FormSchema`
- `ConfirmSurfaceRenderer` -> `Xmessages` 中的确认卡片

这一步非常关键，因为它决定了我们是在做“安全的声明式 UI”，还是又回到“模型决定页面细节”的高风险路径。

#### 第四步：把 surface 正式接进 `clarify` 阶段

当前链路大致是：

- runtime 返回 `type: 'clarify'`
- UI 展示文本追问
- 用户继续输入文本
- 再次调用 `runAgent()`

未来目标链路应变成：

1. runtime 判断当前需要补参或确认
2. 返回 `clarify + surface`
3. `Xmessages` 把这条消息渲染成结构化卡片
4. 用户在卡片中提交
5. 前端生成 `clarifyResponse`
6. 业务层再次调用 `runAgent({ clarifyResponse, sessionState })`
7. runtime 依据 `surfaceKey` 恢复执行

也就是说，surface 不是旁路逻辑，而是 clarify 的正式下一跳。

#### 第五步：把恢复逻辑收敛回 `runAgent()`

这里要非常克制。  
无论是 `form` 还是 `confirm`，提交后都不应该直接打业务接口，而应该统一回到 `runAgent()`。

对应关系应当是：

- `form` 提交 -> `payload` 解释为 `slotPatch`
- `confirm` 提交 -> `payload` 解释为 `confirmDecision`

然后由 runtime 做两件事：

- 校验 `surfaceKey`、`surfaceId`、`responseType`
- 基于 `pendingClarify` 决定是补槽位继续跑，还是恢复 `pendingAction`

这一步直接决定状态是否可追踪、可调试、可幂等。

#### 第六步：先做“受限子集”，再考虑泛化

第一阶段建议严格限制范围：

- 只支持 `form`
- 只支持 `confirm`
- 只允许单个活跃 surface
- 只服务于 `clarify` 阶段
- 不做 surface 内部再请求业务后端
- 不做任意嵌套 generative layout

等这条链路稳定后，再考虑是否继续扩展：

- `options`
- `login`
- 文件上传
- 多 surface 并行
- 更通用的 agent-generated UI

### 8.7 `form + confirm` 如何具体用到澄清阶段

这部分可以直接按两个典型流程理解。

#### 场景一：缺参数补槽位

例如用户问：“帮我查一下项目进度”，但没有给项目编号。

当前文本澄清方式是：

- agent 说“请补充项目编号”
- 用户再打字输入项目编号

未来按 A2UI 风格 surface 的方式是：

1. runtime 发现 `projectCode` 缺失
2. 返回 `clarify + form surface`
3. `form surface` 中声明：
   - 标题
   - 字段 `projectCode`
   - placeholder
   - submitText
4. `Xmessages` 渲染表单卡片
5. 用户填写后提交
6. 前端生成：
   - `surfaceId = 'form'`
   - `responseType = 'slotPatch'`
   - `payload = { projectCode: 'P20260520' }`
7. `runAgent()` 恢复后合并 slot，再继续原能力执行

#### 场景二：副作用操作确认

例如用户要“正式提交项目申请”。

未来方式应是：

1. runtime 已经拿到完整参数
2. 发现当前 tool 标记了 `confirmBeforeExecute`
3. 返回 `clarify + confirm surface`
4. `confirm surface` 中声明：
   - 标题
   - 风险说明
   - 摘要信息
   - 确认按钮文案
5. 同时把待执行动作写入 `pendingClarify.pendingAction`
6. 用户点击确认
7. 前端生成：
   - `surfaceId = 'confirm'`
   - `responseType = 'confirmDecision'`
   - `payload = { confirmed: true }`
8. `runAgent()` 不再重新问模型，而是直接恢复 `pendingAction`

这一点很重要，因为 `confirm` 的本质不是补信息，而是确认是否执行已经准备好的动作。

## 9. 结论

这批 `X*` 组件已经不只是聊天 UI，而是一套初步成型的 AI 前端基础设施。

它当前已经完成了 4 件关键事情：

- 把输入能力组件化
- 把消息展示标准化
- 把模型配置集中化
- 把 Agent 运行机制结构化
- 把 Agent 后续的结构化交互路线定义清楚

下一阶段最重要的方向，不是简单继续加功能，而是：

- 做稳抽象
- 补齐标准
- 提升可观测性
- 支撑更多业务低成本复用

如果用一句话总结这次工作的阶段价值，可以概括为：

**我们已经把 AI 场景从“页面级试验”推进到了“前端能力底座建设”阶段。**
